FINAL PLAN — Stabilize Dialog Orchestration After Switching to a 70B Model

Context

After switching to a cloud 70B model, the language quality of the replies improved, but the main issues remain in the orchestration layer around the model:

1. The system still loses or corrupts FL/YUL context.
2. A new explicit user intent does not always override an old active scenario.
3. Validators sometimes require information the user did not ask for.
4. Repair can make replies worse by adding irrelevant facts.
5. Repetition complaints are handled incorrectly.
6. Escalation triggers, but metadata may contain the wrong debtor type or bank.
7. Bitrix may fail to receive the escalation, yet the system still logs “Escalation completed.”
8. On startup, the worker may crash because the `jobs` table does not exist yet.

Important constraints:
- Do not change the model.
- Do not add phrase-by-phrase hardcoded replies.
- Do not revert the project to a rigid FSM.
- Fix general architectural causes, not isolated wording cases.

======================================================================
TASK 1 — Strengthen DealState consistency and debtor_type persistence
======================================================================

Problem

The user asks about FL, but the bot suddenly answers about YUL:

- User: “for physical persons, which banks and tariffs?”
- User: “only one bank?”
- Bot replies about “three active banks for legal entities.”

Also, during escalation for opening an account in T-Bank for FL, metadata was logged as:
- selected_bank = T-Bank
- debtor_type = YUL

This is critical.

What to do

Make `debtor_type` part of DealState with priority above scenario scoring.

Requirements

1. If the session already knows:
   debtor_type = "FL"

   then:
   - retrieval must prioritize only FL-related chunks;
   - ScenarioPolicy must not select YUL scenarios as the main answer path;
   - manager_context must explicitly contain debtor_type=FL;
   - ConversationResponder must not answer with YUL facts unless the user explicitly switches the topic.

2. If the user explicitly changes the entity type:
   - “and for legal entities?”
   - “now about YUL”
   - “for physical persons”

   then debtor_type may be updated.

3. During escalation, debtor_type must be taken from the current DealState, not from stale or loosely merged slot payloads.

Acceptance

Case 1
User:
- “for physical persons, which tariffs and banks?”
- “only one bank?”

Expected:
- the bot stays in FL context;
- it does not answer about YUL;
- if the KB says there is only one main working FL bank, say so;
- if the KB contains more FL options, list only FL options.

Case 2
User:
- “I want to open for a physical person in Tinkoff, which documents are needed?”

Expected escalation metadata:
{
  "selected_bank": "T-Bank",
  "debtor_type": "FL"
}

TASK 2 — Make explicit topic switches override stale active scenarios
======================================================================

Problem

After:
- User: “why do I need intermediaries?”

the active scenario is `direct_bank_objection`.

Then the user asks:
- “what other bonuses are available for arbitration managers?”

Intent `interest_or_bonus` is detected, but the active scenario remains `direct_bank_objection`, so the bot repeats the previous value proposition instead of answering the bonus question.

What to do

In ScenarioPolicy, add a general rule:

A new explicit intent must override the old active scenario if the user clearly moved to a new topic.

Priority topic switches

1. `interest_or_bonus` > `direct_bank_objection`
2. `repetition_complaint` > any business scenario
3. `documents_requested` > bank conditions when a bank is already selected or the user is ready to open
4. `timelines` > tariffs/details when the user asks “how long?”
5. `specific_bank_focus` > generic partner bank listing

Acceptance

Case:
- “why do I need intermediaries?”
- “what other bonuses are available for AU?”

Expected:
- active scenario switches to `au_bonus_question` or an equivalent bonus-related scenario;
- forced retrieval no longer stays limited to `direct_bank_objection`;
- the answer is about AU bonuses from KB, not a repeated value proposition.

======================================================================
TASK 3 — Fix repetition complaint handling
======================================================================

Problem

Phrases such as:
- “why are you repeating yourself?”
- typo form: “why are you repeating yourself” with misspelling

are handled incorrectly.

In one case, `repetition_complaint` is accepted, but retrieval still forces `direct_bank_objection`.
In another case, semantic similarity is almost perfect, but the intent is rejected because lexical gating requires exact terms and does not tolerate typos.

What to do

3.1 Increase the priority of `repetition_complaint`

If `repetition_complaint` is accepted:
- it must override the active business scenario;
- retrieval must NOT force `direct_bank_objection`, `partner_banks`, tariffs, or other business chunks;
- responder must receive a manager_context such as:

{
  "dialog_act": "repetition_complaint",
  "instruction": "Acknowledge the repetition, apologize, do not repeat the same information, and briefly suggest moving forward."
}

3.2 Make gating robust to typos

For repetition complaints:
- either add lexical variants such as:
  - повторяешься
  - повторяешся
  - повторил
  - одно и то же
  - снова повторяешь

- or allow a high-confidence semantic override:
  if intent == "repetition_complaint" and semantic_score >= 0.90:
      accept even if lexical gate is weak

Expected reply

For:
- “why are you repeating yourself?”

Expected:
- acknowledge the repetition;
- apologize briefly;
- do not repeat tariffs or benefits;
- offer to continue usefully.

Example:
“Sorry, I did repeat myself. I will not duplicate the same point again. I can continue directly with your case or move to the next practical step.”

======================================================================
TASK 4 — Make validators intent-sensitive
======================================================================

Problem

On:
- “how long will it take?”

the validator complains:
- `missing_fl_tariff_details`

This is wrong because the user asked about timing, not tariffs.

This causes repair to inject old tariff content and creates the feeling that the bot is repeating itself.

What to do

Rewrite response validation so requirements depend on the actual current user intent.

Examples

If intent = `timelines`
Require:
- answer about timing;
- if KB contains a confirmed timeframe, use it;
- do NOT require tariffs.

If intent = `tariff_comparison_requested`
Require:
- tariff information;
- do NOT require timelines.

If intent = `documents_requested`
Require:
- documents or required data;
- do NOT require tariffs.

If intent = `specific_bank_conditions`
Require:
- conditions for the relevant bank;
- do NOT require a full list of all active banks.

Acceptance

Case:
- “I have FL”
- “how long will it take?”

Expected:
- the answer discusses timing/process only;
- it does not repeat tariff blocks;
- validator does not return `missing_fl_tariff_details`.

======================================================================
TASK 5 — Reduce repair drift and make repair minimal
======================================================================

Problem

Repair sometimes “fixes” validation formally but makes the reply worse:
- adds an irrelevant bank;
- repeats previously stated facts;
- expands the answer far beyond the user’s question.

Example:
The user asked about Uralsib and timing, but after repair the answer added an unrelated TKB block.

What to do

5.1 Repair should fix only the concrete error

The repair prompt must include:
- original user question;
- original model answer;
- validation error;
- strict instruction:

“Fix only the specified validation issue.
Do not change the topic.
Do not add banks or tariffs the user did not ask about.
Do not expand the answer unnecessarily.”

5.2 Add a validator against repair topic drift

After repair, check:
- whether new banks appeared that were not part of the original context;
- whether new topics were introduced;
- whether the response became much longer without reason;
- whether near-duplicate repetition appeared.

If drift is found:
- reject the repair;
- use responder retry with corrected manager_context.

Acceptance

Repair for:
- “what about Uralsib, and how long does it take?”

must not add a new TKB block if the user did not ask for it.

======================================================================
TASK 6 — Audit and stabilize KB facts for FL / T-Bank / Uralsib
======================================================================

Problem

Dialogs show potentially contradictory facts:
- in some places the main FL working option is only TKB;
- elsewhere the bot mentions TKB and Uralsib;
- elsewhere it claims Tinkoff/T-Bank exists for FL;
- escalation to T-Bank was emitted with the wrong debtor type.

What to do

Audit the current KB for:

1. `bank_selection_fl`
2. `tkb_fl_conditions`
3. `uralsib_fl_conditions`
4. `tbank_fl_conditions` or equivalent
5. active/paused status of T-Bank for FL
6. tariffs for FL banks
7. timelines for FL banks

Requirement

If the KB contains ambiguous or conflicting chunks:
- fix the KB itself;
- do not hide the inconsistency with prompt tricks.

Acceptance

After the audit, the bot must answer consistently:
- which banks are available for FL;
- what Uralsib offers for FL;
- whether T-Bank is available for FL;
- which tariffs are truly confirmed by the KB.

======================================================================
TASK 7 — Fix escalation metadata and delivery status reporting
======================================================================

Problem

Escalation for `ready_to_open` fires, but:
- metadata may contain the wrong debtor type;
- Bitrix returns 401 ACCESS_DENIED;
- the service still logs `Escalation completed`.

What to do

7.1 Metadata

Escalation must take:
- selected_bank;
- debtor_type;
- deal_stage;
- client_intent;

from the current DealState.

7.2 Delivery status

Separate these statuses clearly:
- handoff_triggered
- crm_lookup_failed
- dialog_upload_failed
- manager_message_failed
- manager_notified=false

Do NOT log:
- `Escalation completed`

if:
- Bitrix deal lookup failed;
- dialog file upload failed;
- manager message was not delivered.

7.3 Final escalation status

Example:
{
  "handoff_triggered": true,
  "crm_delivery_status": "failed",
  "manager_notified": false,
  "failure_reason": "bitrix_access_denied"
}

Acceptance

When Bitrix returns 401:
- logs clearly show the handoff trigger happened;
- logs clearly show manager delivery failed;
- there is no false `completed` message.

======================================================================
TASK 8 — Fix startup race / missing jobs table
======================================================================

Problem

After restart:
- `sqlite3.OperationalError: no such table: jobs`

The worker starts polling the queue before the database schema is ready or before the correct database is mounted/connected.

What to do

1. Verify startup ordering:
   - initialize DB;
   - run migrations or `create_all`;
   - only then start worker loop.

2. If SQLite is used in dev:
   - guarantee schema initialization before `fetch_and_lock_jobs`.

3. If the table is missing:
   - fail clearly during startup;
   - do not start the worker in a half-broken state.

Acceptance

Running:
- `python run.py`

on a clean local DB:
- must not fail with `no such table: jobs`;
- tables must be created before the worker loop starts.

TASK 9 — Fix primary chunk selection when relevant context exists
======================================================================

Problem

In many relevant cases, logs show:
- `primary_chunks=0`

even though raw chunks are found.

This weakens the responder and gives the model a mixed, less structured context.

What to do

Make primary chunk selection more meaningful.

Examples

If current intent = `timelines`
and bank_focus = TKB
and debtor_type = FL

primary chunks should include:
- `internal_ops_timelines`
- `tkb_fl_conditions`

If current intent = `interest_or_bonus`
primary chunks should include:
- `au_bonus_question`
- `interest_on_balance`
- relevant partner benefits if applicable

If current intent = `specific_bank_conditions`
and bank_focus = Uralsib
and debtor_type = FL

primary chunks should include:
- `uralsib_fl_conditions`

Acceptance

RAGTrace for key queries must show:
- `primary_chunks > 0`

and these chunks must be truly relevant to the current user question.

TASK 11 — Do not change the project strategy
======================================================================

Do not:
- turn the system into a set of isolated regex patches;
- replace the current LLM-led responder with hardcoded templates;
- hide problems behind generic fallback replies.

Fix:
- state management;
- scenario switching;
- intent-aware validation;
- repair discipline;
- escalation reliability;
- KB consistency.

======================================================================
Definition of Done
======================================================================

The task is complete only when:

1. FL/YUL context does not drift in replies or escalation metadata.
2. A new explicit intent overrides stale active scenarios.
3. Repetition complaints are handled as complaints, not as a new sales intent.
4. A timing question does not force tariff repetition.
5. Repair does not drift into irrelevant topics.
6. Escalation metadata is correct.
7. Bitrix delivery failures are not falsely marked as completed.
8. Startup no longer crashes because the `jobs` table is missing.
9. Primary chunks are actually selected for key intents.
10. All new golden dialog tests pass.

Final emphasis:
The 70B model is already strong enough.
The next quality gain must come from fixing orchestration around it:
- stronger DealState;
- better scenario override rules;
- intent-aware validation;
- disciplined repair;
- reliable escalation;
- consistent KB grounding.
