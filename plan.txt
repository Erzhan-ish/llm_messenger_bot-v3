Ты работаешь с проектом llm_messenger_bot-v3.

Нужно упростить архитектуру под MVP и будущую большую модель 24B.

Главная формула:
LLM думает над смыслом.
Код проверяет, считает и выполняет.

Текущая проблема:
В message_processor.py слишком много смысловой логики в коде: regex для bank_selection, pricing, docs, timing, conditions, constraint, speed, low_cost и т.д.
Из-за этого появляются баги:
- клиент спрашивает про перевод → бот отвечает про открытие счёта;
- клиент спрашивает про Уралсиб → бот отвечает про ТКБ;
- клиент коротко отвечает “130 тыс” → бот теряет pending-задачу;
- клиент спрашивает “у них сколько?” → бот не понимает, что это продолжение прошлого расчёта;
- constraint начинает управлять всем диалогом;
- код становится сложным и хрупким.

Новая цель:
Убрать из message_processor.py почти всю semantic-routing логику.
Код НЕ должен заранее определять сценарий и категорию до LLM, кроме hard guards.
LLM-planner должен определять смысл сообщения на основе:
- текущего сообщения;
- полной сессионной памяти;
- active_task;
- recent_dialog;
- релевантного KB context;
- scenario_hints как подсказки, не как финальное решение.

Код должен:
- сохранять контекст;
- доставать факты из KB;
- считать точные суммы;
- проверять ответ;
- выполнять handoff/CRM;
- делать fallback при сбое LLM.

============================================================
1. УПРОСТИТЬ MESSAGE_PROCESSOR
============================================================

Файл:
app/processing/message_processor.py

Нужно удалить или перевести в hints почти всю semantic-routing логику:
- _BANK_SELECTION_REQUEST_RE
- _PRICE_QUERY_RE
- _DOCS_QUERY_RE
- _TIMING_QUERY_RE
- _CONDITIONS_QUERY_RE
- _LOW_COST_RE
- _SPEED_RE
- ручные ветки explicit_bank_selection
- explicit_pricing
- explicit_docs
- explicit_timing
- explicit_conditions
- ручные query_mode override, кроме hard guards

Оставить в коде только hard guards:
- /reset
- duplicate/rate limit/debounce
- save_message
- merge rapid messages
- audio transcription
- stop/aggression
- direct handoff phrases
- already escalated
- out_of_scope obvious guard
- critical safety guard, если LLM недоступен
- CRM/handoff execution

Все остальные regex должны стать rule_hints, а не decision.

Пример:
Было:
if _TIMING_QUERY_RE.search(user_text):
    decision = {"query_mode": "timing", ...}

Должно стать:
rule_hints["maybe_timing"] = true

Финальное решение делает только dialog_planner.

2. ВВЕСТИ ЕДИНЫЙ ACTIVE_TASK / MEMORY STATE
============================================================

Файл:
app/processing/slots.py
app/processing/message_processor.py

Код должен сохранять не только slots, а активную задачу диалога.

Добавить в slots:
slots["_active_task"] = {
    "intent": null,
    "scenario_topic": null,
    "constraint_topic": null,
    "bank_name": null,
    "client_type": null,
    "amount": null,
    "transfer_target": null,
    "pending_question": null,
    "next_action": null,
    "last_answer_summary": null
}

Примеры active_task:

После:
“сколько будет стоить перевод 200 000 руб. на физлицо в Альфа-Банке?”

Сохранить:
{
  "intent": "transfer_fee_quote",
  "bank_name": "Альфа-Банк",
  "amount": 200000,
  "transfer_target": "ФЛ",
  "pending_question": null
}

Если бот спросил:
“На какую сумму планируете перевод?”

Сохранить:
{
  "intent": "transfer_fee_quote",
  "bank_name": "Альфа-Банк",
  "transfer_target": "ФЛ",
  "pending_question": "amount"
}

Тогда follow-up:
“примерно 130 тыс”
должен идти в planner вместе с active_task, а не в общий bank_selection.

Важно:
Код не должен сам решать по regex, что это amount follow-up.
Код должен передать active_task в LLM-planner.
LLM-planner должен вернуть:
intent=transfer_fee_quote
amount=130000
bank_name=Альфа-Банк
transfer_target=ФЛ

Код потом проверяет и считает.

============================================================
3. LLM-PLANNER ДОЛЖЕН СТАТЬ ГЛАВНЫМ SEMANTIC ROUTER
============================================================

Файл:
app/services/dialog_planner.py

Planner должен принимать:

plan_dialog(
    user_text: str,
    slots: dict,
    active_task: dict | None,
    recent_dialog: str,
    kb_context: list[dict],
    scenario_hints: list[dict],
) -> dict

Planner НЕ пишет ответ клиенту.
Planner возвращает JSON.

Обязательная schema:

{
  "domain": "in_scope|out_of_scope|unclear",
  "stage": "GREETING|QUALIFY|PRESENTATION|OBJECTION|CONSTRAINT|DOCS|HANDOFF|OUT_OF_SCOPE",
  "intent": "greeting|company_info|bank_selection|pricing|transfer_fee_quote|extra_fees|bonus|docs|timing|signing|access_cards|operations|constraint|objection|handoff|redirect_to_domain|clarify|conditions",
  "query_mode": "same_or_more_specific",
  "scenario_topic": "string|null",
  "constraint_topic": "string|null",
  "next_action": "string|null",
  "client_type": "ФЛ|ЮЛ|ИП|null",
  "bank_name": "ТКБ|Уралсиб|Альфа-Банк|Т-Банк|МКБ|Росбанк|null",
  "amount": number|null,
  "transfer_target": "ФЛ|ЮЛ|null",
  "answer_focus": "short description",
  "must_use_facts": [],
  "missing_info": [],
  "should_handoff": false,
  "should_stop": false,
  "next_question": "one short question",
  "confidence": 0.0
}

Главное правило planner-а:
Ты определяешь смысл сообщения клиента.
Код не будет заранее выбирать intent за тебя.
Scenario_hints — это подсказки, но финальное решение принимаешь ты.

Prompt planner-а должен явно говорить:

- Бот консультирует АУ по счетам должников.
- Не универсальный помощник.
- Клиент может писать короткими follow-up: “у них сколько?”, “а там?”, “130 тыс”, “да”, “нет”, “для ЮЛ”.
- Используй active_task, чтобы понять follow-up.
- Если active_task.intent=transfer_fee_quote и клиент пишет сумму или другой банк — продолжай transfer_fee_quote.
- Если клиент спрашивает комиссии/переводы/стоимость платежа — это НЕ constraint.
- Если клиент спрашивает можно/нельзя/регламент/ограничение — это constraint.
- constraint_topic может быть дополнительным полем, но intent не обязан быть constraint.
- Если клиент готов оформлять / что дальше / подходит / давайте — should_handoff=true.
- Если вопрос вне домена — domain=out_of_scope.

5. SCENARIO CATALOG ОСТАЁТСЯ ТОЛЬКО HINTS
============================================================

Файл:
app/domain/scenario_catalog.py

Scenario catalog нужен, но он не должен принимать решение вместо LLM.

Функция:
build_scenario_hints(user_text) -> list[dict]

Возвращает:
[
  {
    "intent": "transfer_fee_quote",
    "scenario_topic": "payment_transfer_fee",
    "constraint_topic": null,
    "next_action": "calculate_or_explain_transfer_fee",
    "score": 2
  }
]

Эти hints передаются в planner.

Запрещено:
if top_hint.intent == "pricing": decision = pricing

Разрешено:
rule_hints["scenario_hints"] = hints
decision = await plan_dialog(..., scenario_hints=hints)

============================================================
6. КОД ПРОВЕРЯЕТ DECISION, НО НЕ ПОДМЕНЯЕТ ЕГО БЕЗ ПРИЧИНЫ
============================================================

Файл:
app/services/policy_validator.py

Policy validator должен проверять, а не делать новый semantic routing.

Проверки:
1. domain=out_of_scope → redirect_to_domain.
2. should_handoff=true → handoff, не продолжать консультацию.
3. intent=transfer_fee_quote/extra_fees/pricing/bonus не перезаписывать в constraint только из-за constraint_topic.
4. Если intent=constraint, constraint_topic обязателен.
5. Если current_bank_mention есть, bank_name должен совпадать с текущим банком.
6. Если active_task.intent=transfer_fee_quote и planner вернул bank_selection/pricing при follow-up “у них сколько/130 тыс” — это ошибка planner-а. Вернуть planner retry или исправить только в рамках active_task.
7. Если confidence < 0.55 → clarify или handoff.
8. Если should_stop=true → остановить диалог.
9. Если answer потом содержит цену/банк не из facts → fallback.

Важно:
Policy validator не должен превращаться в новый message_processor с кучей if/elif.
Только safety checks и consistency checks.

10. PENDING/FOLLOW-UP РЕШАЕТ LLM, НО КОД ПЕРЕДАЁТ ПАМЯТЬ
============================================================

Запрещено писать много кода:
if pending_question == transfer_amount and regex amount:
    decision = transfer_fee_quote

Лучше:
- код парсит простые entities: amount, current_bank_mention, client_type
- кладёт в slots/current_entities
- planner получает active_task + current_entities
- planner сам решает смысл

Код может сделать только consistency override:
Если active_task.intent=transfer_fee_quote и planner вернул bank_selection на текст “130 тыс”, validator отправляет planner retry с ошибкой:
“Ты потерял active_task. Клиент ответил суммой на pending вопрос. Верни transfer_fee_quote.”

То есть модель думает, но код ловит явную несогласованность.

12. HANDOFF ОСТАЁТСЯ В КОДЕ
============================================================

LLM planner может вернуть:
should_handoff=true

Но код делает:
- stop consultation
- bridge phrase
- maybe_escalate
- CRM task
- slots["_escalation_sent"]=true

Нельзя давать LLM самому продолжать консультацию после handoff.

Триггеры в prompt planner:
- что дальше
- оформляем
- подходит
- давайте
- куда оплатить
- готов начать
- позовите менеджера
- хочу с человеком

Код может иметь hard regex для прямого handoff, это нормально.

13. FACT VALIDATOR ОСТАЁТСЯ ЖЁСТКИМ
============================================================

После LLM-render:

validate_answer_against_facts(answer, plan):
- банк в ответе должен совпадать с decision.bank_name/current_bank_mention;
- суммы должны быть из facts/calculation;
- если calculation.calculated_fee=1000, ответ не может написать 1500;
- если intent=transfer_fee_quote, ответ не должен говорить только opening/monthly;
- если intent=docs, ответ не должен добавлять тарифы без запроса;
- если domain=out_of_scope, ответ не должен отвечать по внешней теме;
- если answer near duplicate last_bot_text → retry render or fallback.

15. FINAL ACCEPTANCE CRITERIA
============================================================

Готово, если:

1. message_processor.py стал коротким orchestrator-ом, а не местом для semantic routing.
2. Regex не принимают финальные решения по pricing/docs/timing/conditions/bank_selection.
3. LLM-planner получает active_task, KB context, slots, recent_dialog, scenario_hints.
4. LLM-planner определяет intent/scenario/query_mode.
5. Код проверяет decision, но не пытается заново классифицировать всё.
6. Код считает комиссии и точные формулы.
7. LLM-render пишет живой текст и получает больше свободы.
8. Validator ловит галлюцинации, неверные банки, неверные суммы, повторы.
9. Follow-up “у них сколько?”, “130 тыс”, “для ЮЛ”, “да введена” обрабатываются через active_task + planner.
10. Handoff/CRM остаются кодом.
11. На обычный ответ максимум 2 LLM-вызова: planner + renderer.
12. Проект готов к подключению большой 24B модели как planner+renderer.
