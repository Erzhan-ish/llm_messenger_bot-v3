# IMPLEMENTATION PLAN
# Create a new simplified LLM-first branch for llm_messenger_bot-v3

## Goal

Create a separate branch with a **much simpler and more stable conversation pipeline**.

The new branch must preserve only the useful infrastructure features we already built:

- Telegram message batching / BurstMerge;
- sessions and `/reset`;
- conversation history;
- RAG from the current knowledge base;
- prompt-debug / LLM tracing;
- minimal response validation;
- escalation detection;
- full silence after escalation.

But remove the over-engineered orchestration layer:

- no `ScenarioPolicy` routing;
- no `ScenarioPlaybook`;
- no `ScenarioCatalog` as a business router;
- no `DialogPlanner`;
- no code-driven scenario decisions;
- no code-driven next-step hints;
- no forced conversation flow from Python;
- no hardcoded scenario examples injected into the model.

The new design should be:

```text
System Prompt
+ Relevant KB chunks
+ Conversation history
+ Current user message
= LLM answer
```

The only business control left in code is:

```text
Escalation detector
```

# 2. Target architecture

## Final simplified pipeline

```text
1. Receive Telegram message
2. Handle /reset immediately
3. If session is silenced after escalation:
      - ignore all messages except /reset
4. Apply BurstMerge:
      - merge rapid consecutive messages from same user
5. Save merged user message into session history
6. Run escalation detector
7. If escalation=true:
      - execute real handoff
      - send fixed final handoff message
      - silence session until /reset
      - stop
8. If escalation=false:
      - retrieve relevant KB chunks
      - build one simple LLM prompt
      - call LLM responder
      - run minimal response validation
      - send reply
9. Save assistant reply into history
```

---

# 3. Remove the complex business-orchestration layer

## Remove or fully bypass in the new branch

The new branch must not use these layers for normal dialogue:

- `DialogPlanner`
- `ScenarioPolicy`
- `ScenarioPlaybook`
- scenario stickiness
- scenario score calculations
- forced scenarios
- deal-stage reasoning for ordinary answers
- active-scenario context injection
- business intent routing that tells the LLM what to answer

If it is easier, the files may remain in the repository but must not be called by the active message pipeline.

## Important

Do not leave half-active routing logic in the background.

The new simplified path must not secretly do:

```text
message → intents → scenario → forced KB → responder
```

It must do:

```text
message → KB search → responder
```

with escalation checked separately.

# 4. Keep and preserve these features

## 4.1. BurstMerge / debounce

Keep the current ability to merge multiple fast Telegram messages:

Example:

```text
ТКБ
Какие условия там
?
```

must be processed as one user turn.

The already implemented logic should remain:

- old jobs suppressed if newer messages are pending;
- punctuation-only messages merged;
- only one final bot reply for one logical burst.

Keep logs like:

```text
BurstMerge |
session=... |
merged_count=3 |
final_text="ТКБ\nКакие условия там\n?"
```

---

## 4.2. Sessions and `/reset`

Keep:

- session persistence;
- conversation history;
- `/reset` clears context and silence flags;
- new session starts clean.

---

## 4.3. Full silence after escalation

Keep strict rule:

```text
After real escalation:
- send one final handoff reply;
- then no more bot replies until /reset.
```

Use the exact final handoff message:

```text
Принял. Передаю вашу заявку старшему менеджеру, чтобы помочь вам дальше.
```

After sending it:

```python
slots["_session_silenced_after_handoff"] = True
slots["_escalation_sent"] = True
```

At the beginning of processing:

```python
if session_is_silenced_after_handoff and user_message != "/reset":
    return without outbound reply
```

# 5. New simplified message processor

Create a new simplified processing function or fully refactor the existing one.

Suggested shape:

```python
async def process_message_simple(...):
    if is_reset(message):
        reset_session()
        send_reset_reply()
        return

    if session_is_silenced_after_handoff(session):
        log_suppressed_after_handoff()
        return

    merged_message = merge_burst_messages(...)

    append_user_message_to_history(session, merged_message)

    escalation = await escalation_detector.detect(
        history=session.history,
        current_message=merged_message,
    )

    if escalation.needed:
        await execute_handoff(...)
        await send_fixed_handoff_reply(...)
        silence_session_after_handoff(...)
        return

    kb_chunks = retrieve_relevant_kb_chunks(
        message=merged_message,
        history=session.history,
    )

    prompt_payload = build_simple_responder_payload(
        system_prompt=load_system_prompt(),
        kb_chunks=kb_chunks,
        history=session.history,
        current_message=merged_message,
    )

    reply = await llm.generate(prompt_payload)

    reply = validate_or_repair_minimally(reply)

    send_reply(reply)
    append_assistant_message_to_history(session, reply)
```

# 6. Simplify the LLM prompt

## Core philosophy

The model should receive:

1. role / behavior instructions;
2. trusted KB facts;
3. conversation history;
4. current user message.

No scenario prompts from code.
No examples based on scenario routing.
No `active_scenario`, `next_manager_move`, `scenario_policy`, or similar fields.

---

## Suggested system prompt

Use a single clean prompt file, for example:

```text
app/llm/prompts/manager/simple_system_prompt.md
```

Suggested contents:

```text
Ты — Алексей, консультант компании «В плюсе».

Компания помогает арбитражным управляющим открывать и сопровождать счета должников в процедурах банкротства.

Твоя задача:
- отвечать на вопросы клиента естественно, спокойно и по делу;
- объяснять банки, тарифы, условия, документы, ограничения и выгоды сотрудничества;
- использовать только факты из блока KNOWLEDGE;
- учитывать историю текущего диалога;
- не повторяться без необходимости;
- не выдумывать тарифы, проценты, сроки, документы и условия;
- если в KNOWLEDGE нет достаточных фактов, честно скажи, что этот момент нужно уточнить у менеджера;
- обращаться к клиенту только на «вы»;
- писать естественным деловым русским языком;
- не использовать иностранные слова или мусорные вставки;
- не обещать подключение менеджера самостоятельно — это контролирует система отдельно.
```

The responder LLM should get something like:

```text
SYSTEM:
[system prompt]

KNOWLEDGE:
[Chunk 1]
[Chunk 2]
[Chunk 3]

DIALOG HISTORY:
User: ...
Assistant: ...
User: ...

CURRENT USER MESSAGE:
...
```

or equivalent JSON/chat-message structure.

## Important

Do not pass:

- planner result;
- scenario ids;
- forced topic names;
- active scenario;
- code-written interpretation of user intent;
- examples selected by code based on scenarios.

# 8. RAG retrieval in the simple branch

## Goal

Retrieve relevant KB chunks directly from:

- current merged message;
- optionally recent dialog context.

Do not rely on business scenario routing.

## Suggested search query

Build retrieval query using:

```text
current_user_message
+ optional short context from last 1–2 user messages
```

Example:

User history:

```text
User: у меня ФЛ
Assistant: Для ФЛ есть ТКБ...
User: а какие условия там?
```

retrieval query can be:

```text
ФЛ условия ТКБ какие условия
```

This query can be built simply from:
- current message;
- recent known textual entities found in history;
- no scenario engine.

## Acceptable lightweight context extraction

You may keep only very small utility extraction if useful:

- detect explicit bank names: ТКБ, Альфа-Банк, Уралсиб;
- detect explicit debtor type: ФЛ, ЮЛ.

This is not scenario routing.
It is only query enrichment for RAG.

Example:

```text
current_message = "а какие условия там?"
last_bank_mention = "ТКБ"
last_debtor_type = "ФЛ"

retrieval_query = "ТКБ ФЛ условия какие условия"
```

This is allowed.

Keep a very small state object only for retrieval convenience:

```json
{
  "last_bank_mention": "tkb",
  "last_debtor_type": "fl"
}
```

Allowed use:
- enrich KB search query;
- help retrieve more relevant chunks.

Forbidden use:
- choosing the conversation scenario;
- forcing what the answer must say;
- replacing the model’s dialogue reasoning.

# 10. Escalation detector

## Purpose

Escalation remains the only business decision handled separately.

The detector answers one question:

```text
Is the user ready for a human manager / ready to proceed?
```

## Recommended implementation

Use a small dedicated LLM classifier.

Input:
- recent conversation history;
- current merged message.

Output strict JSON:

```json
{
  "escalate": true,
  "reason": "ready_to_open"
}
```

or:

```json
{
  "escalate": false,
  "reason": null
}
```

---

## Escalation should trigger for cases like

- `хочу открыть`
- `мне подходит`
- `давайте открывать`
- `что от меня требуется?`
- `что скинуть?`
- `куда отправлять документы?`
- `сюда скидывать?`
- `передайте менеджеру`
- `готов запускать`
- `оформляем`
- `берём`
- clear contextual acceptance after bank/conditions explanation:
  - `хорошо`
  - `нормально`
  - `давайте`
  when history clearly shows that a concrete option was discussed.

---

## Escalation must NOT trigger for

- normal questions;
- tariff requests;
- conditions questions;
- bank comparison;
- “подробнее”;
- “какие банки есть?”;
- “зачем мне посредники?”;
- ordinary acknowledgements without readiness context.

---

# 11. Escalation flow

If detector returns:

```json
{
  "escalate": true
}
```

then:

1. Call actual handoff service.
2. Save escalation metadata if needed.
3. Send exact fixed reply:

```text
Принял. Передаю вашу заявку старшему менеджеру, чтобы помочь вам дальше.
```

4. Set silence flags.
5. Stop processing.

Do not call the responder LLM after escalation has been detected.

---

# 12. Remove LLM-generated handoff text

The responder prompt should explicitly say:

```text
Do not promise that a manager will be connected.
Do not say that the request is being transferred.
Escalation is controlled by the system separately.
```

The message processor should also validate:
- if normal responder output contains handoff-like wording;
- reject and repair or replace it.

Examples to block in normal responder output:

- `передам менеджеру`
- `передаю менеджеру`
- `менеджер свяжется`
- `передам заявку`
- `подключу старшего менеджера`

If the system did not trigger escalation, such wording is invalid.

---

# 13. Minimal response validation

Keep only validators that protect visible quality.

## Keep validators for:

### 13.1. Empty or broken replies

Reject:
- empty text;
- whitespace-only text;
- malformed technical output.

### 13.2. Foreign-language artifacts

Reject replies containing unexpected words like:

```text
benötujete
```

Keep whitelist only for legitimate technical terms if needed:
- CRM
- Telegram
- Bitrix
- API

### 13.3. Informal tone

Reject:
- `ты`
- `тебе`
- `твой`
- `тебя`

### 13.4. Unauthorized handoff promises

Reject manager-transfer phrases when escalation was not triggered by detector.

---

# 14. Optional minimal repetition guard

For presentation stability, keep a lightweight anti-repeat check.

If the new reply is near-identical to the immediately previous assistant reply:
- try one short repair;
- or send a concise alternative.

But do not rebuild a complicated anti-repetition fact-group system in this simple branch.

Allowed simple approach:
- normalized string similarity;
- compare last reply only.

# 20. Definition of Done

The new branch is complete when:

1. A separate simple branch exists.
2. Normal conversation no longer uses ScenarioPolicy / Planner / Playbook / Catalog routing.
3. The answer pipeline is:
   ```text
   prompt + KB + history + current message
   ```
4. BurstMerge still works.
5. `/reset` works.
6. RAG still works.
7. Escalation detector works independently.
8. Handoff sends only the fixed final message.
9. Session is fully silent after escalation.
10. Normal responder never promises a manager if detector did not escalate.
11. Visible replies contain no foreign garbage.
12. Visible replies use formal “вы”.
13. Telegram smoke test feels more natural and less code-controlled.
14. This branch is stable enough for presentation and can be compared against the complex orchestrated branch.
