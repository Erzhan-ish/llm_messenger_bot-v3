# IMPLEMENTATION PLAN
# simple-llm branch — implement 5 parallel workers safely

## Goal

Scale the `simple-llm` branch from a single sequential worker to **5 parallel worker processes** while preserving the current bot behavior:

- BurstMerge must continue to merge rapid user messages.
- Different users must be processed in parallel.
- One and the same conversation must never be processed concurrently by multiple workers.
- No duplicated bot replies.
- No broken session history.
- No broken escalation silence.
- `/reset` must remain safe.
- The simplified LLM-first pipeline must remain unchanged.

The target behavior:

```text
Parallel across different users.
Strictly serialized inside one conversation.
```

---

# 1. Current architecture to preserve

The simplified pipeline must remain:

```text
Webhook
→ enqueue inbound job
→ worker picks job
→ simple_message_processor
→ dedup / rate limit
→ reset / silence checks
→ save user message
→ BurstMerge
→ EscalationDetector
→ if escalate=true:
       fixed handoff reply + session silence
   else:
       SimpleRAG + LLM responder
→ send bot reply
```

Do NOT reintroduce:
- ScenarioPolicy;
- DialogPlanner;
- Playbooks;
- code-driven business scenarios.

This task is only about **safe parallel worker execution**.

---

# 2. High-level target architecture

## New runtime model

```text
run.py
 ├── uvicorn app
 ├── worker process #1
 ├── worker process #2
 ├── worker process #3
 ├── worker process #4
 └── worker process #5
```

## Processing principle

```text
User A can be processed in parallel with User B.

But:
User A message #1 and User A message #2
must never run through the LLM pipeline at the same time.
```

# 3. Database requirement for 5-worker mode

## 3.1. Multi-worker mode should require PostgreSQL

The current queue locking uses:

```text
SELECT ... FOR UPDATE SKIP LOCKED
```

This is the correct mechanism for multiple workers, but it is reliable in PostgreSQL.

## Required behavior

Add a startup check:

```python
if WORKER_COUNT > 1 and DATABASE_URL points to sqlite:
    raise RuntimeError(
        "WORKER_COUNT > 1 requires PostgreSQL for safe concurrent job locking."
    )
```

or, if preferred for local dev:

```python
if sqlite and WORKER_COUNT > 1:
    log warning
    force WORKER_COUNT = 1
```

## Recommendation

Use strict mode:

```text
5 workers = PostgreSQL required.
```

Do not pretend SQLite is production-safe for this.

## Why `WORKER_BATCH_SIZE=1`

Right now a worker can fetch multiple jobs at once and then process them one by one.

With 5 workers, if each one fetches 10 jobs:
- first worker may reserve many jobs;
- other workers can sit idle;
- parallelism becomes worse.

For fair distribution:

```text
each worker fetches exactly 1 job at a time
```

Set:

```python
WORKER_BATCH_SIZE = 1
```

# 5. Update `run.py` to start 5 worker processes

## Current behavior

`run.py` starts:
- uvicorn;
- one worker.

## Required behavior

Spawn:

```text
WORKER_COUNT worker subprocesses
```

## Target implementation

```python
import os
import signal
import subprocess
import sys
from app.config import settings


def main():
    processes = []

    # Web app
    p_web = subprocess.Popen([
        sys.executable,
        "-m",
        "uvicorn",
        "app.main:app",
        "--reload",
    ])
    processes.append(p_web)

    # Workers
    worker_count = settings.WORKER_COUNT

    for index in range(worker_count):
        env = os.environ.copy()
        env["WORKER_ID"] = f"worker-{index + 1}"

        p_worker = subprocess.Popen(
            [sys.executable, "-m", "app.worker"],
            env=env,
        )
        processes.append(p_worker)

    try:
        for p in processes:
            p.wait()
    except KeyboardInterrupt:
        for p in processes:
            p.terminate()

        for p in processes:
            try:
                p.wait(timeout=10)
            except subprocess.TimeoutExpired:
                p.kill()


if __name__ == "__main__":
    main()
```

## Requirements

- Every worker must have its own `WORKER_ID`.
- Logs must show which worker claimed and processed which job.
- Graceful shutdown must terminate all worker processes.

# 7. Add conversation-level locking

## Why this is mandatory

With 5 workers, two jobs from the same user can otherwise run at the same time:

```text
Worker 1 → processing User A message #1
Worker 2 → processing User A message #2
```

This can cause:
- broken history;
- two replies in wrong order;
- escalation races;
- bot replying after it should be silenced;
- BurstMerge instability.

## Required rule

```text
Only one active processing pipeline per conversation key.
```

Use:

```text
conversation_key = f"{channel}:{external_user_id}"
```

Do not lock only by external_user_id, because the same external id may exist across channels.

# 8. Add `ConversationLock` model

## File

```text
app/storage/models.py
```

## Add table

```python
class ConversationLock(Base):
    __tablename__ = "conversation_locks"

    conversation_key: Mapped[str] = mapped_column(
        String(160),
        primary_key=True,
    )

    locked_by: Mapped[str] = mapped_column(
        String(64),
        nullable=False,
    )

    locked_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
        server_default=func.now(),
    )

    expires_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
    )
```

## Notes

- Primary key must be `conversation_key`.
- One active row = one active conversation lock.
- Expiration protects against worker crashes.

# 9. Add conversation lock repository

## New file

```text
app/storage/repositories/conversation_locks_repo.py
```

## Functions

### 9.1. `try_acquire_conversation_lock`

```python
async def try_acquire_conversation_lock(
    *,
    conversation_key: str,
    worker_id: str,
    ttl_seconds: int,
) -> bool:
```

### Behavior

1. Delete expired lock for this conversation if exists.
2. Try to insert a new lock row.
3. If insert succeeds → lock acquired.
4. If unique constraint fails → another worker owns the lock.

### Pseudocode

```python
async with AsyncSessionLocal() as session:
    now = utcnow()
    expires_at = now + timedelta(seconds=ttl_seconds)

    # Remove expired stale lock
    await session.execute(
        delete(ConversationLock).where(
            ConversationLock.conversation_key == conversation_key,
            ConversationLock.expires_at < now,
        )
    )

    try:
        session.add(
            ConversationLock(
                conversation_key=conversation_key,
                locked_by=worker_id,
                expires_at=expires_at,
            )
        )
        await session.commit()
        return True
    except IntegrityError:
        await session.rollback()
        return False
```

---

### 9.2. `release_conversation_lock`

```python
async def release_conversation_lock(
```

Delete lock only if owned by the same worker:


# 10. Add job deferral support

## Why

If Worker 2 receives a job for a conversation currently locked by Worker 1, it must not:
- process concurrently;
- mark the job done;
- drop the message.

It should simply try again later.

## File

```text
app/storage/repositories/jobs_repo.py
```

## Add function

```python
async def defer_job(
    job_id: int,
    *,
    delay_seconds: int = 2,
    reason: str = "conversation_locked",
) -> None:
```

## Behavior

Update job:

```python
status = "queued"
run_after = now + delay_seconds
locked_at = NULL
updated_at = now
last_error = optional diagnostic reason
```

Do not increment retry attempts.

# 11. Refactor processing flow to use the conversation lock

## File

```text
app/processing/simple_message_processor.py
```

## Current important fact

The processor currently:
- saves incoming user message;
- waits 2 seconds;
- checks for newer active jobs;
- lets only latest burst message produce the reply.

This BurstMerge logic must remain.

## New safe flow

### Recommended order

```text
1. dedup
2. rate limit
3. create/get session
4. save user message into DB
5. BurstMerge quiet wait
6. if newer active job exists → skip this job
7. acquire conversation lock
8. if lock not acquired → defer job and return
9. inside lock:
      - re-check session silence
      - re-check whether a newer active job now exists
      - process reset if needed
      - load slots/history
      - merge recent user messages
      - escalation detector
      - RAG + LLM responder
      - dispatch answer
10. finally release conversation lock
```

# 12. Important change: `/reset` must also be protected by conversation lock

## Problem

With 5 workers:
- one worker may be generating a response;
- another worker may process `/reset` simultaneously.

This can lead to:
- stale reply being sent after reset;
- session inconsistency.

## Required behavior

`/reset` should be handled inside the same conversation lock.

### Implementation

Do not immediately return from `/reset` before lock acquisition.

Instead:

1. Save or identify the reset job;
2. acquire lock;
3. reset session inside the lock;
4. send reset reply;
5. release lock.

This guarantees no other worker is sending a reply concurrently.

# 13. Add stale job recovery

## Problem

If a worker crashes after marking a job as `running`, the job may remain stuck forever.

## Add repository function

```python
async def requeue_stale_running_jobs(
    *,
    stale_after_seconds: int,
) -> int:
```

## Behavior

Find jobs:

```text
status = "running"
locked_at < now - stale_after_seconds
```

Reset them:

```text
status = "queued"
locked_at = NULL
run_after = now
```

## Where to call

At worker startup:

```python
await requeue_stale_running_jobs(
    stale_after_seconds=settings.JOB_STALE_LOCK_TTL_SECONDS,
)
```

Optionally also periodically in worker loop.

# 14. Add stale conversation lock cleanup

## Problem

If a worker crashes while holding a conversation lock, that conversation can become permanently blocked.

## Solution

Locks have `expires_at`.

In `try_acquire_conversation_lock()`:
- delete stale expired lock;
- then acquire normally.

Also add startup cleanup:

```python
async def delete_expired_conversation_locks() -> int:
```

Call once when worker starts.

To:

```python
has_newer_active_job(
    current_job_id: int,
```

## Required query logic

Only compare newer jobs that have:

```text
same channel
same external_user_id
```

- Telegram user `123`;

# 24. Definition of Done

The task is complete only when:

1. `run.py` starts exactly 5 worker processes by default via `WORKER_COUNT=5`.
2. Each worker has a distinct `WORKER_ID`.
3. Worker batch size is 1 so jobs are fairly distributed.
4. PostgreSQL is required or explicitly enforced for multi-worker mode.
5. Conversation-level DB lock prevents concurrent processing of the same user.
6. Different users are processed in parallel.
7. Same-user jobs never run LLM pipelines concurrently.
8. BurstMerge still works exactly as before.
9. Escalation silence still works exactly as before.
10. `/reset` is safe under concurrent workers.
11. Stale jobs are recoverable.
12. Stale conversation locks are recoverable.
13. Logging clearly shows worker id, locks, defer/release flow.
14. All new concurrency tests pass.
15. Manual test with 5 simultaneous users shows real throughput improvement without duplicate replies.
